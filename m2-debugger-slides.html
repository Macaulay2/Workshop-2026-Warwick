Debugging in Macaulay2

A hands-on tour of the interactive debugger

Anton Leykin

What we’ll learn

By the end you’ll be able to:

  • Drop into the debugger when an error fires
  • Inspect the local state at the point of failure
  • Read the source of a function you can’t otherwise see
  • Walk up and down the call stack and exit cleanly

LIVE: have an M2 session already open in a terminal or Emacs. Say: “Everything here runs on one tiny demo file — follow along if you like.” Don’t type anything yet.

The setup

We use a demo file shipped with Macaulay2:

i1 : load "Macaulay2Doc/demos/demo1.m2"

It defines a function g, which quietly calls a helper f.

The catch: f has local variables that we can’t see it from the top level. That’s exactly the situation the debugger is built for.

LIVE — type: load “Macaulay2Doc/demos/demo1.m2” It returns the file path. Point out nothing visible happened yet — the functions are now defined.

Part 1 — Look before you run

Discover what’s available

listUserSymbols shows the symbols you’ve been given:

i2 : listUserSymbols

o2 = symbol   class            value
     ------   -----            -----
     g        FunctionClosure  g

Only g shows up. Where’s f? Hold that thought.

LIVE — type: listUserSymbols Point at the output: “Only g. There’s no f here — remember that.”

Read the code

code prints a function’s source without running it:

i3 : code g

g = y -> (
     c := f(y-1);
     d := f(y-2);
     c+d)

So g depends on f — but f is hidden. The mystery is set.

LIVE — type: code g Trace the calls to f with your cursor. Ask the room: “g clearly uses f — so why couldn’t we see f a moment ago?” (Because it’s local. That’s the whole point of the debugger.)

Part 2 — Trigger the debugger

It works… at first

i4 : g 4
o4 = 17/6

i5 : g 3
o5 = 7/2

Looks fine. Then:

i6 : g 2
error: division by zero
entering debugger (enter 'help' to see commands)
     b := 1/x;

The debugger starts automatically on the error.

LIVE — type these one at a time, pausing after each: g 4 g 3 g 2 On g 2 the debugger fires. Slow down here — let the error land before you say anything. The prompt changes (ii6 instead of i6); point that out.

Read the error line

demo1.m2:8:11:(3):[3]: error: division by zero
     b := 1/x;
  • File, line, and column of the failure
  • The offending source: b := 1/x
  • We’re now inside the debugger, paused at that line

Type help to see every debugger command.

LIVE — type: help Don’t read the whole menu aloud — just say “these are the commands available while paused” and move on. If you’re in Emacs, mention you can press RET on the file:line to jump to the source.

Part 3 — Diagnose

Inspect the local state

listLocalSymbols shows the variables in scope right now:

ii7 : listLocalSymbols

oo7 = symbol  class  value
      ------  -----  -----
      a       String "hi there"
      x       ZZ     0
      ...

x is 0. That’s our division by zero.

LIVE — type: listLocalSymbols Put your cursor on the x row. “x is 0 — there’s the division by zero.” This is the payoff moment; let it sit.

See the hidden function

Inside the debugger, f is in scope — so now code works on it:

ii8 : code f

f := x -> (
     a := "hi there";
     b := 1/x;
     b+1)

The debugger gives us visibility into the helper we couldn’t see before.

LIVE — type: code f Call back: “Earlier this would have failed — f wasn’t visible. Inside the debugger it is, because we’re paused in its scope.”

Part 4 — Move through the stack

Step, then pop up a level

ii9 : step 0          -- bypass the current expression

Decide the real problem is one level up? Use end to leave this frame and re-enter at the call site inside g:

ii10 : end
     d := f(y-2);

LIVE — type: step 0 end After end, point out the source line changed to d := f(y-2) — we’ve moved from inside f up into g, at the exact call that triggered it.

Inspect g’s locals

ii11 : listLocalSymbols

oo11 = symbol  class  value
       ------  -----  -----
       c       QQ     2
       y       ZZ     2
       ...

Now we see g called f(y-2) with y = 2, i.e. f(0). Confirmed.

LIVE — type: listLocalSymbols “Same command, different frame — now we see g’s variables. y is 2, so f(y-2) is f(0). Full story confirmed.”

Get out

ii12 : break

break quits the debugger entirely and returns to top level.

end = up one frame

break = all the way out

LIVE — type: break Prompt returns to plain i13. Emphasize the contrast: end moved us one frame; break dropped us all the way back to top level.

Part 5 — Tuning

Control when it fires

errorDepth sets how deep an error must be before the debugger activates.

  • Lower it to catch errors closer to the surface
  • Raise it to ignore shallow ones and stop deeper in

A configuration knob, not an everyday command.

Optional live bit — type: errorDepth to show its current value. No need to change it live; just flag that it exists for when the default behavior isn’t what you want.

Wrap-up

Cheat sheet

Command What it does
code f print a function’s source
listUserSymbols symbols at top level
listLocalSymbols variables in current frame
step n run n lines (0 bypasses current)
end leave frame, go up one level
break quit debugger, back to top
breakpoint pause before a function runs
finish finish frame, return to caller
continue / return resume a loop / return a value
errorDepth set when the debugger activates

Leave this slide up while you talk. Offer to share the deck so they have the table.

Your turn

Write two tiny functions where the outer one calls a hidden helper that fails on some input (e.g. a bad list index or another 1/0) or add a breakpoint.

Then:

  1. Trigger the error
  2. listLocalSymbols to find the bad value
  3. code the helper to confirm the line
  4. end up to the caller, then break out

If time allows, do this live as audience-driven coding: ask someone to suggest a buggy helper, type it in, and debug it together using the four steps. Best way to make it stick.

Going further

The docs link a few more inspection tools worth a look:

  • value — evaluate an expression
  • pseudocode — show a function’s pseudocode
  • disassemble — disassemble pseudocode or a function

Source: the M2 manual node “the debugger.”

Mention these only if the room is keen — they’re inspection extras, not core to the debugger workflow. Then take questions.
